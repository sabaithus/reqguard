### 3.2. Детальный разбор замечаний к отдельным требованиям

#### [DEF-A01] Требование `REQ-05 / Ф-2` — Критичный (Блокер)
- **Нарушенный критерий:** Однозначность (ISO 29148 п. 5.2.5)
- **Источник обнаружения:** LLM-анализатор (цитата верифицирована)
- **Место в документе:** Стр. 1, строка 26 (Часть A. Новый функционал → Требования к изменениям → Функциональные требования)
  > «• Ф-2. Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.»
- **Суть дефекта:** Формулировка «по дате совершения покупки» неоднозначна: дата совершения (авторизации) может отличаться от даты клиринга/проведения (финансового списания), при этом далее упомянуты «проведённые покупки».
- **Риск при разработке / тестировании:** Риск расхождения сумм накопленных расходов между процессингом и сервисом уведомлений, рассинхронизация при смене месяца.
- **Что исправить:** Четко зафиксировать, какой именно статус и штамп времени транзакции (дата авторизации или дата клиринга) используется для финансового учета месяца.
- **Предлагаемая формулировка / вопрос:** Уточнить у бизнес-аналитика: учитывается дата авторизации покупки по времени Алматы или дата финансового проведения (клиринга)?

#### [DEF-A02] Требование `REQ-09` — Критичный (Блокер)
- **Нарушенный критерий:** Проверяемость / измеримость (ISO 29148 п. 5.2.5)
- **Источник обнаружения:** Подтверждено дважды (AST-анализатор + LLM)
- **Место в документе:** Стр. 1, строка 32 (Часть A. Новый функционал → Нефункциональные требования)
  > «Сервис передаёт push на отправку в течение минуты после получения события.»
- **Суть дефекта:** Нефункциональное требование ко времени отклика задано без статистического перцентиля (p95/p99/max), целевой нагрузки (RPS/TPS), момента старта таймера и политики ретраев при сбое.
- **Риск при разработке / тестировании:** Нагрузочное тестирование и приёмка SLA невозможны однозначно: единичный сетевой выброс либо сбой смежного сервиса трактуется двояко.
- **Что исправить:** Указать метрику (например, p95 ≤ 60 с при пиковой нагрузке N событий/сек), точки измерения тайминга и поведение при недоступности downstream-сервиса (очередь ретраев / DLQ).

#### [DEF-A03] Требование `REQ-11` — Критичный (Блокер)
- **Нарушенный критерий:** Полнота формулировки (ISO 29148 п. 5.2.5)
- **Источник обнаружения:** LLM-анализатор (цитата верифицирована)
- **Место в документе:** Стр. 2, строка 36 (Часть A. Новый функционал → Требования к интеграции)
  > «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.»
- **Суть дефекта:** Не указан механизм обеспечения идемпотентности (уникальный ключ или transaction_id) при повторной доставке события процессинга.
- **Риск при разработке / тестировании:** Риск повторного суммирования одной и той же покупки при сбоях сети или повторных доставках.
- **Что исправить:** Указать уникальный ключ идемпотентности для обработки событий процессинга.
- **Предлагаемая формулировка / вопрос:** Добавить: «Идемпотентность обеспечивается по уникальному идентификатору операции (operation_id/transaction_id)».

#### [DEF-A04] Требование `REQ-01` — Существенный
- **Нарушенный критерий:** Проверяемость / измеримость (ISO 29148 п. 5.2.5)
- **Источник обнаружения:** LLM-анализатор (цитата верифицирована)
- **Место в документе:** Стр. 1, строка 16 (Часть A. Новый функционал → Цели)
  > «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»
- **Суть дефекта:** Формулировка «в момент покупки» не содержит конкретного временного регламента (SLA/SLA-таймаута) для проверки выполнения цели.
- **Риск при разработке / тестировании:** Невозможно объективно протестировать и подтвердить достижение бизнес-цели при приемке.
- **Что исправить:** Указать допустимый временной интервал от момента авторизации покупки до информирования клиента.
- **Предлагаемая формулировка / вопрос:** Уточнить у владельца продукта: каков целевой максимальный временной зазор между проведением транзакции и информированием?

#### [DEF-A05] Требование `REQ-05 / Ф-2` — Существенный
- **Нарушенный критерий:** Единичность / атомарность (ISO 29148 п. 5.2.5)
- **Источник обнаружения:** Подтверждено дважды (AST-анализатор + LLM)
- **Место в документе:** Стр. 1, строка 26 (Часть A. Новый функционал → Требования к изменениям → Функциональные требования)
  > «• Ф-2. Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.»
- **Суть дефекта:** Требование содержит 4 независимых бизнес-правила: часовой пояс месяца, состав операций (покупки), порядок обработки возвратов, исключения (переводы и снятие).
- **Риск при разработке / тестировании:** Затрудняет покрытие тестами всех условий и проверку их реализации.
- **Что исправить:** Разбить пункт Ф-2 на четыре отдельные поднормы.
- **Предлагаемая формулировка / вопрос:** Выделить правила в отдельные требования Ф-2.1 ... Ф-2.4.

- **Суть дефекта:** В перечне хранимых атрибутов порог указан в тенге, а сумма покупки в тиынах, но не зафиксированы типы данных и признак активности настройки (enabled).

- **Что исправить:** Дополнить атрибутивный состав модели данных типами полей и отсутствующим полем состояния уведомлений.
- **Предлагаемая формулировка / вопрос:** Уточнить у аналитика: требуется ли хранить флаг активности push-уведомления (enabled) в структуре данных расходов?
